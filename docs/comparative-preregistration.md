# GUARD comparative experiment — pre-registration

Status: LOCKED before any experimental-split result was observed. The only live
results seen before locking are (a) a two-case smoke test on throwaway fixtures
generated with seed 777 (not in any split) and (b) the reviewer calibration on the
six already-public catalog fixtures (Step 2, run after this document is committed).
Amendments after locking are appended in a dated "Deviations" section and never
rewrite the text above it.

## 1. Questions and hypotheses

| # | Question | H0 (null) | H1 |
|---|---|---|---|
| Q1 | Does GUARD improve independently verified correctness over frozen EOAI? | Paired dev-eval pass-rate difference GUARD − frozen = 0 | > 0 |
| Q2 | Does GUARD prevent regressions that Naive RSI introduces? | Newly broken dev-eval tasks: GUARD = Naive | GUARD < Naive |
| Q3 | How often does GUARD reject potentially beneficial changes? | descriptive | — |
| Q4 | Does the absolute mandatory-write veto change results? | GUARD = GUARD-without-veto on dev-eval and promotions | differ |
| Q5 | How accurately does self-review predict real correctness? | descriptive (FP/FN vs oracle) | — |
| Q6 | Is GUARD's extra computation justified? | descriptive (cost per recovered task) | — |

Prior expectation, stated so it can be falsified: given the Phase 1 pilot and the
re-audit (M1, M5), the most likely outcome is that GUARD promotes rarely or never,
so its final harness equals frozen v0 and Q1 is null by construction. This is a
legitimate result, not a failure of the experiment, provided the cause (UNKNOWN,
veto, insufficient gain) is reported.

## 3. Datasets

Generated by `python -m experiments.comparative.fixtures --seed 20261120` into a
custodian-private directory outside Git (`~/EOAI-private/comparative-v1`, mode 0700).
Every case has its own tenant, customer names, invoice IDs and SQLite lineage. Decisions
are targeted by an independent hand calculator and cross-checked against the frozen
policy engine; any disagreement aborts generation (none occurred). Splits load through
`eoai_eval.datasets.load_heldout` and pass `validate_disjoint` against each other and
against the existing catalog adaptation/gate splits (pilot-06 buffer and gate cohort):
disjoint case IDs, task assignments, lineages and snapshot contents.

| Split | Cases | Families (inventory / review / conflict / escalate_one / escalate_account / paged_review) | Manifest sha256 | Suite digest |
|---|---|---|---|---|
| adaptation (GUARD training; Naive training) | 20 | 3/3/3/4/4/3 | 4d23ab45… | 95c95255… |
| gate (GUARD replay buffer only) | 10 | 1/2/2/2/2/1 | 2bdc9cae… | 5ec2049b… |
| deveval (independent evaluation) | 30 | 5/5/5/5/5/5 | 5e33ec35… | 7e136522… |

Family → catalog analogue: inventory ≈ acme-list; review ≈ acme-escalation read-only;
conflict ≈ meridian-conflict (AMBIGUOUS_AMENDMENT or MISSING_TERM_EVIDENCE); escalate_one
≈ acme-escalation; escalate_account ≈ acme-account-escalation; paged_review ≈ acme-paged-v2
(v2 profile, pages of three, optional transient fault). No approval writes
(requires_approval = 0 everywhere) and every task has a resolvable customer.

Blinding: adaptation processes load only adaptation+gate manifests and strip
`expectations` from every case before use (`runner._strip`); no role call ever receives
expectations; the deveval manifest is opened only by `runner deveval` (oracle scoring, no
reviewer, no proposer) and by the post-hoc analysis. Family labels live only in the private
`index.json`. The sealed final held-out suite is never located, opened or run.

## 4. Arms

All arms: identical frozen EOAI business logic, tools, limits, solver configuration, and the
same frozen self-review checklists (derived once per trial, before any rollout, shared by all
arms). The frozen-v0 batch on adaptation+gate is rolled out once per trial and shared as every
arm's incumbent evidence.

- **A — Frozen EOAI.** Packaged v3 harness, no adaptation.
- **B — Naive RSI** (`naive.py`). Per round: unranked reflection on failed adaptation tasks
  (failed requirement text, reviewer rationale, observed trace excerpts — the same trace-derived
  failure text GUARD's reviewer produces), `pool_size` proposals through GUARD's own proposer
  prompt, grounding filter and GUARD's own initial strategy text (`SHARED_STRATEGY`, never
  evolved), with within-pool de-duplication; each candidate is rolled out on the 20 adaptation
  tasks and the best mean continuous self-review score (over graded criteria) is always promoted.
  The proposer also receives observed traces of every adaptation task. No regret ranking,
  contrasts, rejection ledger, replay or gate.
- **C — GUARD** (`loop.run_rounds`, unchanged). Training = adaptation, replay = gate.
- **C′ — GUARD without veto** (ablation). Identical to C except `loop.promotion_gate` is replaced
  in-process by `runner.no_veto_gate`, which removes only the absolute
  `eoai_required_action_completion` veto. The paired-completeness (UNKNOWN) block is kept. Runs
  in the same isolated sandbox; no production access exists.

Policy for B, C, C′: pool_size 2, rounds 3, replicates 1, noise floor 15, hurt budget 1, margin
1.5, repair budget 1, ledger 40. Role sampling streams per trial t: shared/checklists 10⁶t;
GUARD and GUARD-no-veto 10⁶t + 10⁴ (deliberately the same stream — common random numbers, so the
veto is the only systematic difference); Naive 10⁶t + 2·10⁴. Seed assignment among concurrent
pool slots follows thread order and is not bitwise reproducible (also true of GUARD itself).
Arms run in the fixed order C, C′, B.

Budgets. Proposals: 2 per round × 3 rounds = 6 per adaptive arm (plus ≤1 format retry each and
≤2 regenerations on a repeated digest, as in GUARD). Solver rollouts per arm: Naive 3 × 40 = 120;
GUARD 3 × (40 + 10 replay [+ 30 if a repair is attempted]) = 150–240. The extra replay/repair
rollouts and the contrast call are GUARD's mechanism and are reported as its overhead, not
equalised away. GUARD's proposer additionally sees replay-task evidence (≈50 % more task
evidence than Naive); this confound is reported with any GUARD-vs-Naive difference. All tokens, calls and latency are recorded per role and per rollout.

## 5. Trials

`runner validate` (all three splits, disjointness, core digests) runs first. Trial 1 is mandatory. Trials 2 and 3 are run sequentially if each previous trial completed,
up to three in total; the decision to run a further trial depends only on wall-clock and
machine availability, never on scores. Each trial is: `runner trial --trial t` then
`runner deveval --trial-dir …`. Dev-eval: every distinct final harness (frozen, C, C′, B) × 30
cases × 1 replicate per trial. Identical harness texts are evaluated once and the result is
shared, which is recorded. Run-to-run variance across trials comes only from role sampling
(proposals, contrast, repair); the solver and reviewer run at temperature 0, so trials are
repeated measurements of the adaptation process, not independent task samples.

## 6. Veto handling (re-audit condition 2)

Fixtures are not screened or dropped (dropping would bias toward tasks v0 already solves).
Instead the primary GUARD arm keeps the veto, C′ measures it directly, and for every gate call
in C and C′ the report records: (1) the paper's Soft-HURT decision recomputed from the recorded
paired scores; (2) the actual controller decision; (3) whether the incumbent already failed the
same required write; (4) whether the candidate improved oracle-verified outcomes on the gated
tasks (post hoc). Shared-v0 `required_action_completion` per task is reported.

## 7. Reviewer UNKNOWN handling

- Unit: one semantic judgment (one criterion on one rollout) after GUARD's single retry.
- Threshold: if more than **10 %** of a trial's semantic judgments across all arms are
  unresolved, the trial is **UNEVALUABLE** for Q1, Q3–Q5 (still reported descriptively).
- Because any UNKNOWN in a candidate's batch blocks its round, the report also gives the
  observed per-round block rate and the implied probability 1 − (1 − p)^n for the observed
  judgments per round. Gate blocks caused by UNKNOWN (`unreliable_review`) are reported
  separately from substantive rejections (`hurt_budget`, `insufficient_help`,
  `insufficient_gain`, `required_action_incomplete`).
- Orchestration aborts (any exception, e.g. proposer retry budget exhausted) are recorded in
  `status.json`; the arm is reported as ABORTED for that trial, not as rejected, and its abort
  rate is reported per arm. For dev-eval an aborted arm is scored as the frozen harness
  (intention to treat: a failed improvement run deploys nothing). No silent reruns.

## 8. Metrics

Oracle = `experiments.eoai_eval.scoring.score` against private expectations.

Primary (dev-eval, task is the unit; trials are repeated measurements, not extra tasks):
- Per-arm task success rate; per-task pass rate averaged over completed trials.
- Paired difference vs frozen and GUARD vs Naive: mean of per-task differences; exact two-sided
  sign-flip permutation test over the 30 tasks; percentile bootstrap 95 % CI (10 000 resamples
  over tasks, seed 0).
- Newly broken (frozen passes, arm fails) and recovered (frozen fails, arm passes) task counts
  per trial; forgetting per family (family pass rate drop vs frozen).
- Between-trial variation: per-trial rates and the frozen arm's own run-to-run disagreement
  (solver nondeterminism floor).

Secondary: promotions and rejections by reason; paper-vs-actual gate disagreement; UNKNOWN rate;
self-review FP/FN on adaptation and gate rollouts (self-review pass = strict score 100; oracle
pass = `passed`); safety violations (writes outside scope or unauthorised actions per oracle
write checks, sandbox probe failures); tokens, calls, latency, wall-clock per arm; candidates
rejected by the grounding filter or proposal validation.

## 9. Decision rule for the conclusion

Let Δ = mean paired per-task dev-eval difference GUARD − frozen, p its permutation p-value.

- **GUARD SHOWS MEASURABLE BENEFIT**: trial(s) evaluable, Δ > 0 with p < 0.05, newly broken ≤
  recovered, and GUARD ≥ Naive on dev-eval.
- **GUARD SHOWS LIMITED OR CONDITIONAL BENEFIT**: evaluable, Δ ≥ 0 and either (a) Δ > 0 but
  p ≥ 0.05, or (b) GUARD avoids significant regressions that Naive introduces (Naive − frozen < 0
  with p < 0.05 while GUARD does not regress).
- **NO MEASURABLE BENEFIT**: evaluable and Δ ≤ 0, including GUARD never promoting (final = frozen
  in every trial), unless (b) above applies.
- **INCONCLUSIVE**: no evaluable trial, or GUARD aborted in all trials.

With 30 tasks, a paired difference below roughly 15–20 percentage points is unlikely to reach
p < 0.05; this power limit is reported with the result.

## 10. What is not done

No GUARD prompt, threshold or code change during or after the comparison. No tuning of fixtures
after observing scores. No sealed held-out run. No claim of generalisation beyond these synthetic
development splits.
